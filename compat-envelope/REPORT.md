## Legend (anti-fakery markers)

- `parity%` — fraction of the ptrace-green tests whose output is
  **bitwise-identical** to the ptrace reference run.
- `determinism%` — fraction that run **run1 == run2** (self-deterministic),
  independent of parity. Always ≥ parity%.
- `X%?` — parity was **never measured** for that bucket → UNKNOWN, **not** a
  confirmed 0.
- `X%~` — **partial** parity coverage (some cells measured, some not).
- `n/a` — backend **ran zero** denominator cells here (binary absent, or not
  manifest-enabled in this lane's regression set). **Not** a confirmed fail.

These markers exist so a `0%` is never ambiguous: a real red (ran + failed) is
visually distinct from "not measured" and from "not runnable here." This is the
foundation for the phase-2 acceptance bar (*every red a CONFIRMED red*).

## How to regenerate

```bash
# Hermit envelope (regression mode + real parity):
compat-envelope/collect-envelope.rs --mode regression --lane portable \
  --repo <hermit-checkout> --backends ptrace,dbi,sabre --with-parity \
  --csv compat-envelope/scorecard.csv

# Reverie B1.5 envelope (needs /dev/kvm for the KVM column):
compat-envelope/collect-reverie-compat.rs --repo <hermit-checkout> \
  --csv compat-envelope/reverie-scorecard.csv

# Render either CSV to this table (+ --json / --tsv for machine-readable):
compat-envelope/render-scorecard.rs --csv compat-envelope/scorecard.csv --all
compat-envelope/render-scorecard.rs --csv compat-envelope/reverie-scorecard.csv \
  --denominator counter --all
```

## Enshrinement (validate + CI)

The gate is wired into the outer-repo `Makefile` and a CI workflow:

- **`make validate` → `make compat-envelope`** builds the release hermit binary
  with the in-process DBI backend and runs `validate-envelope.sh` (the
  green-stays-green regression gate). `make compat-envelope-full` adds SaBRe and
  the reverie ptrace-vs-KVM boundary for the privileged runner.
- **`.github/workflows/compat-envelope.yml`** has two jobs: a portable
  `ubuntu-latest` ptrace-denominator gate (always-on, PR + push-to-main) and a
  privileged self-hosted `full-backend` job (DBI + SaBRe + KVM/reverie),
  rrnewton-guarded like the demo sweep.

### Release binary, not debug (validated finding)

The gate runs against the **release** hermit binary via `HERMIT_BIN`. Running
the enabled set caught a genuine non-green cell:
`language-runtimes/python-io-subprocess-time` verify **timed out at exactly
~90s** (`duration_ms=90059` and `90067` across two independent runs — a
deterministic ceiling, not jitter) under a **debug** binary, while it runs
natively in 0.13s and **passes under release**. A debug hermit build is
~5-10× slower and blows the harness per-test timeout on subprocess-heavy cells;
release is also the binary hermit's own CI validates against. Under release the
`language-runtimes` bucket is the full **6/6** (debug undercounted it as 5). This
is exactly the gate doing its job: it distinguished a build-profile speed ceiling
from a compat regression.
