## The current cost, measured

The reverie SHA is **one logical fact stored in 23 places**, in three distinct forms:

| Form | Count | Where | Touched by `cargo update`? |
| --- | --- | --- | --- |
| `rev = "<40-hex>"` in a `[dependencies]` entry | **20** | 8 `Cargo.toml` (below) | no — manifest is the input |
| resolved `#<40-hex>` in a committed lockfile | (17 + 9) | root `Cargo.lock`, `liteinst-runtime-build/Cargo.lock` | **yes** |
| `liteinst-runtime-build-<short7>` cache-dir key | **3** | `ci/dag/portable.json:67`, `hermit-cli/tests/common/liteinst.rs:50`, `validate.sh:4134` | no — hand-embedded short SHA |

The 20 manifest entries, by file:
`detcore-dbi` ×2, `detcore-model` ×1, `detcore-sabre` ×5, `detcore` ×2,
`detcore/tests/testutils` ×2, `hermit-cli` ×6, `hermit-install` ×1,
`liteinst-runtime-build/runtime` ×1.

### Decisive constraint: 4 of 8 manifests are autocargo-generated
`@generated by autocargo` (from internal Buck targets), so the SHA in them is **emitted by a
Meta-internal generator**, not owned by this fork:
`detcore`, `detcore-model`, `detcore/tests/testutils`, `hermit-cli` (= **11 of the 20** entries).
`detcore`'s header explicitly says: *"mirror any change to this commandment in the Buck target's
autocargo comment so it survives regeneration."* Hand-editing these in the fork works transiently
but is **reverted on the next internal regeneration** unless the Buck autocargo config is also
changed (out of reach of the autonomous fork workflow).
Hand-edited (fork-owned): `detcore-dbi`, `detcore-sabre`, `hermit-install`,
`liteinst-runtime-build/runtime` (= 9 entries).

### The three friction consequences (all felt in today's drain)
1. **Conflict surface.** A bump rewrites 8 manifests + 2 lockfiles = 10 files → conflicts with
   nearly every in-flight PR that touches any of them.
2. **Receipt invalidation.** Landing a bump is a commit on `main`; every open PR must rebase to
   pick up the new SHA, and a rebase orphans its validate receipt (measured ~100% orphan;
   cf. `validate-record-keying-breaks-under-rebase`).
3. **Partial-bump hazard.** With 20 hand-listed entries, a bump from a stale list can update some
   and miss others → a build that resolves two reverie SHAs → broken (coord nearly shipped 13/21).

## Option A (requested): manifests say `branch = "main"`, lockfile pins the exact SHA

Cargo records the resolved commit in `Cargo.lock` as `git+URL?branch=main#<40-hex>` even for a
branch dep (verified: current `rev=` form already stores `...#<sha>`; the branch form differs only
in the query key). So a bump becomes `cargo update -p reverie-core --precise <sha>`, and the build
stays exactly reproducible because the lockfile still pins one commit.

**What this genuinely fixes:**
- **Partial bump becomes impossible.** All 15 `reverie-*` crates share ONE git source with ONE
  resolved SHA in the lockfile (verified). `cargo update` moves them atomically — you cannot land
  a half-bumped set. This alone retires failure mode #3.
- **Manifest conflict surface collapses** from 8 files to 0 — pin bumps stop conflicting with
  unrelated manifest edits (failure mode #1, the dominant one in today's 24 rebase-first PRs).
- Single source of truth: the SHA lives only in lockfiles.

**What it does NOT fix (important, corrects the "one line in one file" framing):**
- **Two lockfiles, not one.** `liteinst-runtime-build/` is a *separate workspace* with its own
  `Cargo.lock` (9 reverie lines) built separately via `stage-liteinst-runtime.sh`. A bump is
  `cargo update` in **two** workspaces.
- **Three short-SHA cache keys remain.** The `liteinst-runtime-build-7951770` dir name is
  hand-embedded in 3 files and is not lockfile-derived; a bump still edits them (or they must be
  derived from the lockfile at build time — a small separate change).
- **Receipt invalidation is UNCHANGED (failure mode #2).** The lockfile is still committed and
  still changes on a bump, so landing a bump is still a `main` commit that forces the queue to
  rebase and orphans receipts. Lockfiles are themselves frequent conflict magnets.
- **Enforcement rewrite.** `scripts/check-reverie-pin.rs` (666 lines; wired in
  `.github/workflows/ci-portable.yml`) today asserts *all 20 rev= entries identical + ancestor of
  main*. Under Option A it must instead read the resolved `#<sha>` from the (two) lockfiles. Real
  work, but the check gets *simpler* (one authority: the lockfile).
- **Autocargo drift** on the 4 generated manifests: changing them to `branch=main` diverges from
  the internal generator until the Buck autocargo comment is updated.

Net honest count: a bump goes from **23 places** to **~5** (2 `cargo update` + 3 cache keys), or
to **2** if the cache keys are derived from the lockfile.

## The real fork in the road (why the sibling task exists)

Option A keeps **reproducibility** (receipt = "validated against exact SHA X") but does **not**
break the bump→rebase→orphan cycle. The only thing that breaks that cycle is **floating** the pin
(ghdag's task): manifests track `main`, the lockfile is *not* committed / regenerated at build, so
picking up a new reverie main tip requires no `main` commit and no queue rebase — at the cost that
a receipt no longer certifies a specific reverie SHA. The owner's "floating-main + release-pin"
idea is the hybrid: float for the fast/CI lane, pin one SHA for release/reproducibility.

## Recommendation

1. **Adopt Option A's atomic-consistency property immediately, cheaply, without changing the
   manifest form:** the partial-bump hazard (#3) is already retired by the fact that `cargo update`
   moves all reverie crates together — so the guardrail worth adding now is to make
   `check-reverie-pin.rs` treat the **lockfile** `#<sha>` as the authority and assert the manifests
   agree with it, rather than cross-checking 20 manifest entries against each other. Low risk, no
   autocargo fight.
2. **Do NOT hand-convert the 4 autocargo-generated manifests to `branch=main`** in the fork alone —
   it will be regenerated away. Converting the 4 fork-owned manifests is safe but only removes 9 of
   20 entries, so it's a partial win not worth the churn on its own.
3. **The high-value decision is #2 (receipts), and it is the sibling task's, not this one's.**
   Option A does not solve receipt invalidation; only floating (or lockfile-not-committed for CI)
   does. Route the "float vs pin" decision through
   `analyze-floating-reverie-main-vs-pinned-with-release-pin`. This task's contribution is the
   measured map above and the finding that **the manifest-consolidation win is real for conflict
   surface but zero for receipt orphaning.**
4. **Derive the 3 short-SHA cache keys from the lockfile** (compute short SHA at build time) as a
   standalone cleanup regardless of which pin strategy wins — removes 3 hand-sync sites.

Minor anomaly noted: `hermit-cli/Cargo.lock` exists but has 0 reverie entries (vestigial; not part
of the pin surface).
