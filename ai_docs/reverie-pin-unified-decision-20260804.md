## The four properties every option trades against

- **FRESH** — testing always runs against latest reverie main (the #1591 directive).
- **REPRO** — a given hermit SHA deterministically selects one reverie SHA (the receipt keeps
  meaning what it says).
- **CONFLICT** — manifest/lockfile files a bump rewrites (conflict surface vs in-flight PRs).
- **ORPHAN** — does adopting a new reverie main require a hermit `main` commit → queue rebase →
  receipt orphan (~100% measured)?

## The options

| | FRESH | REPRO | CONFLICT (files/bump) | ORPHAN cycle |
| --- | --- | --- | --- | --- |
| **0. status quo** (`rev=` ×20 + committed locks) | ✗ (the bug) | ✓ | **10** (8 toml + 2 lock) | ✓ present |
| **#1591** (status-quo form + fail-closed fresh gate) | ✓ enforced | ✓ | 10 | ✓ present, *forced on every advance* |
| **A. `branch=main` + committed lockfile** | ✗ alone / ✓ with #1591 | ✓ | **2** (lockfiles only) | ✓ **unchanged** |
| **F. floating** (`branch=main`, lockfile not committed / rebuilt) | ✓ | ✗ unless receipt records reverie SHA | **~0** | ✗ **broken** |
| **H. hybrid** (float+record for CI, pin at release) | ✓ | ✓ (release) / recorded (CI) | ~0 CI, pin at tag | ✗ **broken** |

### Reading the table — the key correction

**Option A does NOT break the orphan cycle.** The owner's framing — "one line in one file,
reproducibility survives, THE RECEIPT KEEPS MEANING WHAT IT SAYS" — is true for **REPRO** (a
committed lockfile pins one SHA, so a receipt keyed to a hermit SHA still certifies a specific
reverie). But "receipt keeps meaning" (REPRO) and "the bump stops orphaning receipts" (ORPHAN)
are **different properties**. Under A + #1591, every reverie advance STILL requires a committed
lockfile change on each PR → still rebases the queue → still orphans receipts. A shrinks the diff
(10 → 2 files, and lockfiles are themselves conflict magnets); it does not "float." Also, "one
line in one file" is really **two** `cargo update` targets (two workspaces) + 3 cache keys.

**Only true floating (F/H) breaks the orphan cycle**, because a reverie advance then needs NO
hermit commit — the PR's existing head rebuilds against new reverie main automatically. Its cost
is REPRO: the same hermit SHA resolves to different reverie over time ("passes at 14:00, fails at
15:00"). **The fix the owner already named is mandatory here: the validate receipt MUST record the
resolved reverie SHA alongside the hermit SHA.** Then a receipt means "hermit X validated against
reverie Y," bisection uses `(hermit, reverie)` pairs, and the #1591 gate keys on *resolved reverie
at validate time == latest main* rather than *committed pin == latest main*.

Note floating does not abolish re-validation under a strict "always latest" rule: when reverie
advances, prior receipts are stale-by-reverie even though no head moved. But it converts a
*commit+rebase+conflict+orphan* event into a *re-run-validate-for-stale-PRs* event, and the
recorded reverie SHA lets you SKIP PRs already validated against current reverie.

## Recommendation (answers all three tasks)

1. **LAND #1591 first — it is the foundation and is on the critical path.** It already enforces
   the freshness invariant fail-closed at every enumerated path (local validate, portable +
   privileged DAG, hosted aggregate, merge-gate trusted checker, receipt `reverie_pin_current`),
   and ships the ONE derived mechanical bump (`check-reverie-pin.rs --update-to-latest`, both
   workspaces) plus `checkout-hermit-pr-latest-reverie.sh`. The whole staging drain is blocked on
   it. This is correct regardless of manifest form and answers
   `reverie-pin-must-track-latest-main` outright.

2. **Adopt Option A's lockfile-as-single-authority (cheap, composes with #1591).** Point
   `check-reverie-pin.rs` at the lockfile `#<sha>` as the authority instead of cross-checking 20
   manifest entries; the atomic-consistency property (all reverie crates move together under
   `cargo update`) already holds and retires the partial-bump hazard (13/21 broken build) outright.
   Collapses manifest conflict 8 → 0. **Do NOT hand-convert the 4 autocargo manifests** (regen
   churn); converting only the 4 fork-owned ones removes 9/20 entries — not worth the churn alone,
   so treat the manifest form as cosmetic and let the lockfile be the pin. Derive the 3 short-SHA
   cache keys from the lockfile as a standalone cleanup. This answers
   `reverie-pin-is-one-fact-in-twenty-places`: consolidation is real for CONFLICT + partial-bump,
   **zero for ORPHAN**.

3. **The high-value move — float the CI lane to kill the orphan cycle — is worth doing, but ONLY
   with the receipt recording the resolved reverie SHA, and gated to AFTER #1591+A.** This is the
   owner's hybrid: `branch=main` + lockfile-not-committed (or `.gitignore`d / rebuilt) for the
   dev/CI lane so reverie advances need no hermit commit; commit the lockfile only at a release
   tag for archival REPRO. Non-negotiable prerequisites: (a) validate receipts record
   `reverie_sha` beside `hermit_sha`; (b) the #1591 gate keys on resolved-reverie-at-validate-time;
   (c) bisection tooling consumes `(hermit, reverie)` pairs. This answers
   `analyze-floating-reverie-main-vs-pinned-with-release-pin`: **floating is the only orphan fix,
   its price is REPRO, and that price is paid by the recorded-reverie-SHA change — which the owner
   already required.**

**Net, in one line:** Option A alone is NOT "the answer to all three" — it delivers conflict +
partial-bump wins and keeps receipts meaningful, but does not stop the bump→rebase→orphan cycle;
only floating does, and floating is safe only once the receipt records the resolved reverie SHA.
Sequence: **land #1591 → lockfile-as-authority (A) → float CI lane with recorded reverie SHA (H)**.
