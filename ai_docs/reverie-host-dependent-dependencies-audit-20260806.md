## 1. OFFENDER 1 — `Cargo.lock` is git-ignored (highest severity)

```
$ git -C reverie check-ignore -v Cargo.lock
.gitignore:2:Cargo.lock	Cargo.lock
$ git -C reverie ls-files Cargo.lock
(nothing)
```

`reverie/.gitignore` line 2 ignores the lockfile. The workspace resolves **287 packages**, and none of
those resolutions are recorded in the repository. Every host — every CI runner, every fresh clone,
every agent slot — runs its own resolution against crates.io at build time and can legitimately get
different versions inside the declared semver ranges.

**This is the reproducibility hole, and it is not theoretical.** It means:

* two hosts building the same reverie SHA can link different code;
* a green validate on one box is not evidence about the same SHA on another;
* an upstream crate publishing a semver-compatible release changes the build with no commit in this
  repo — the build output is a function of *when* you built, not just *what* you built;
* bisecting a regression cannot distinguish "our commit broke it" from "a dependency moved".

### The contrast that settles it

| Repo | `Cargo.lock` |
| --- | --- |
| **hermit** | **tracked** (`git ls-files Cargo.lock` → `Cargo.lock`; not in `.gitignore`) |
| **reverie** | **ignored** (`.gitignore:2`) |

Same fleet, same nightly-pinning discipline, same CI, opposite lockfile policy. So this is not a
considered house style applied consistently — it is a divergence, and hermit already demonstrates the
hermetic choice is workable here.

### The likely original reason, and why it does not survive

Both repos' manifests are generated by `autocargo` from Meta's internal Buck targets, and a common
reason to ignore a lockfile is "the manifests are generated, so the lock would churn." That argument
does not hold, for two reasons: hermit is generated the same way and commits its lock; and lock churn
is *the signal you want* — a lockfile diff is precisely how a dependency version change becomes
reviewable instead of invisible.

**Recommendation (P0): commit `reverie/Cargo.lock` and drop line 2 of `.gitignore`.**
This is a one-line change plus one added file, it makes 287 resolutions reproducible at a stroke, and
it is the single highest-leverage item in this audit. Verify it the way the cold-clone bar demands:
a fresh clone with an empty `CARGO_HOME` must resolve to the committed lock without network
re-resolution (`cargo build --locked` is the enforceable form — it *fails* if the lock would change,
which turns the property into a gate rather than a hope).

> Note the interaction with `--locked`: adding it to CI is what makes the committed lock load-bearing.
> A committed lock that CI silently updates is a cache, not a pin.

## 2. OFFENDER 2 — system packages installed unversioned, and differently per distro

`reverie/.github/workflows/ci.yml` installs C dependencies at job time:

| Line | Job | Command |
| ---: | --- | --- |
| 24 | Regular tests (GitHub-hosted) | `sudo apt-get install -y libunwind-dev liblzma-dev cmake zlib1g-dev` |
| 146 | Host-dependent (self-hosted, Fedora) | `sudo dnf install -y libunwind-devel xz-devel cmake zlib-devel` |
| 148 | Host-dependent (self-hosted, Debian) | `sudo apt-get install -y libunwind-dev liblzma-dev cmake zlib1g-dev` |

Two distinct host-dependencies here, and they are worth separating because they have different fixes:

**(a) No version constraint.** Every one of these installs "whatever this distro ships today".
`libunwind` in particular is linked into the product. An upstream distro bump changes the binary with
no commit in this repo.

**(b) Different package sets per distro.** The dnf branch installs `libunwind-devel`, `xz-devel`,
`zlib-devel`; the apt branch installs `libunwind-dev`, `liblzma-dev`, `zlib1g-dev`. These are the
distros' respective packagings — near-equivalents, not identical builds. So the *authoritative* gate
and the *host-dependent* gate can be linking against materially different library builds, and nothing
records which.

**The dnf-first detection itself is correct and already landed** (`ci.yml:145`), with the reasoning in
the comment: Fedora runners also have `apt-get` on `PATH`, so probing for the binary's *presence* took
the apt branch and failed with "Unable to locate package cmake" (exit 100). That is the
**presence-vs-capability** error the task notes named, and detecting the native manager fixes it.
Fixing the detection does not make the dependency hermetic, though — it makes it *reach the right
package manager*, which is a different property.

**Recommendation (P1):** record what was actually installed. The cheap version is a CI step that dumps
resolved package versions (`dpkg-query -W` / `rpm -q`) into the job log and, better, into the validate
receipt — so a green carries the C-dependency versions it was built against, in the same spirit as
`executed_tests` carrying the condition with the value. The expensive-but-correct version is a
container image with pinned packages, which also collapses (b).

## 3. OFFENDER 3 — `cmake` and the C compiler come from `PATH`

Three `build.rs` scripts shell out to cmake:

| build script | how cmake is found |
| --- | --- |
| `reverie-dbi/build.rs:73` | `env::var_os("CMAKE").unwrap_or_else(\|\| "cmake".into())` |
| `experimental/reverie-sabre/build.rs:110` | same shape |
| `reverie-e9patch/build.rs` | builds vendored e9patch; C toolchain from environment |

So the DynamoRIO, SaBRe and e9patch builds depend on whatever `cmake` and `cc` the host provides.
`reverie-dbi/build.rs:74` additionally honors `CMAKE_GENERATOR` from the environment, so even the
build *system* is host-selectable. These builds are known to be cmake-version-sensitive.

To their credit, all three build scripts gate correctly on target (`CARGO_CFG_TARGET_OS`/`TARGET_ARCH`
checks at `reverie-dbi/build.rs:41`, `reverie-e9patch/build.rs:56`), so they are host-*aware* rather
than host-blind — the dependence is on the toolchain, not on accidental platform assumptions.

**Recommendation (P2):** record the resolved `cmake --version` and `cc --version` in the build log and
the receipt. Pinning them properly means containerizing, which is the same fix as §2(b) and should be
decided once for both rather than twice.

## 4. What is genuinely well pinned (do not "fix" these)

* **Rust toolchain — date-pinned**, and for a documented reason:
  `channel = "nightly-2026-07-29"` with an in-file comment explaining that nightly-2026-07-30 changed
  cargo's cdylib artifact uplift under `cargo test` and broke reverie CI. `components = ["clippy",
  "rustfmt"]` is pinned alongside, with the note that date-pinning installs a fresh dated toolchain
  that rustup only equips when components are requested here. This is the standard to hold the other
  categories to: a pin, plus the reason, plus the unpin condition.
* **Submodules — exact gitlinks**, `update = checkout`, no `shallow` (audited separately in
  `ai_docs/submodule-checkout-by-default-audit-20260806.md`).
* **The one git dependency — rev-pinned**: `liteinst2 = { git = …, rev = "95e…" }`.
* **20 in-tree path deps** — hermetic by construction.

## 5. Runtime host dependence (a different axis, listed so it is not conflated)

These do not make the *build* non-reproducible; they make *test outcomes* host-dependent, and they are
mostly handled deliberately:

| Dependence | Where | Handling |
| --- | --- | --- |
| PMU / retired-branch counters | detcore preemption; reverie timer tests | self-hosted lane; documented as a host limitation |
| `/dev/kvm` | KVM backend | backend marked unsupported in the portable plan |
| CPUID interception | RDRAND/RDSEED tests | documented; "report the host limitation rather than weakening the assertion" |
| Host **load** | `ci.yml` host-dependent job | explicit precondition gate: refuses to run when 1-min load exceeds `REVERIE_MAX_LOAD_PER_CORE × cores`, with an error that says it is *not* a Reverie regression |

The load gate is a good example of the right pattern: rather than producing an invalid measurement on
a contended host, it refuses and says so. That is the same "absence of evidence is not evidence of a
defect" discipline applied at the host level.
